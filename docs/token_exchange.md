# Token exchange over the connection

With the `tokenExchange` option the application persists one long-lived refresh token, and the SDK obtains and renews the short access token (the connection token) itself, over the connection it already has. Set it instead of `getToken`: setting both throws when the client is created. The default is `null`, which leaves the client as it was.

The option has three callbacks. `load` returns the refresh token the application stored, or `null` when there is none, and it is called before every exchange. `store` persists a rotated refresh token, and the SDK awaits it before it uses the access token that came with it. `exchange` gets the refresh token and a `ctx.rpc(method, data)` function that sends a plain rpc call over the connection the exchange runs on. The exchange calls its own rpc method with the refresh token, decodes the reply, and resolves `{ token, refreshToken }`, where `refreshToken` is present only when the issuer rotated it. When the issuer refuses the refresh token, the refusal is classified by the error name the server sent (see `refusalTypes` below), and the SDK runs a refusal run before it ends the session.

```javascript
// The import path is the package the application installs.
import { Centrifuge } from 'centrifuge';

const centrifuge = new Centrifuge('wss://example.com/connection/websocket', {
  tokenExchange: {
    // The names the issuer sends for a refused refresh token: the application's own, none is built in.
    refusalTypes: ['REFRESH_TOKEN_REFUSED'],
    load: () => localStorage.getItem('refreshToken'),
    store: (refreshToken) => localStorage.setItem('refreshToken', refreshToken),
    exchange: async (ctx) => {
      // A refusal rejects this rpc with TokenExchangeRefusedError (an UnauthorizedError); letting it propagate is enough.
      const reply = await ctx.rpc('auth.exchange', { refreshToken: ctx.refreshToken });
      return { token: reply.data.token, refreshToken: reply.data.refreshToken, grace: reply.data.grace };
    },
  },
});
centrifuge.connect();
```

The flow: on connect the client sends a connect command without a token. When the reply is anonymous and `load` returns a refresh token, the SDK runs `exchange` over that same connection, stores the rotated refresh token, sends the access token in a refresh command, and reports `connected` once, with the identity of the refresh reply. The renewal is driven by the expiry of the access token: the SDK runs the exchange over the connected socket at a random moment between 0.7 and 0.9 of the token's ttl, so clients that connected together spread their renewals. A renewal that fails is reported and retried with backoff, as `getToken` failures are. The access token stays in memory; the SDK never stores either token itself.

Several tabs or processes of one installation can share the refresh token through the same storage without a lock. The SDK reads `load` right before each exchange and stores the rotated token right after it. A client that is refused because another one rotated the token meanwhile reads `load` again and presents the new value at once, with no delay and no event (see the refusal run below). The renewal of the access token is due between 0.6 and 0.9 of its ttl, at random; an issuer that renews many connections at once can add jitter to the ttl it returns, so the renewals spread out. The re-presentation is bounded only while the stored value stays the same: a storage that alternates between values, which a faulty writer can cause, is not bounded, so the writer must rotate forward only. An exchange that was abandoned is stored the same way, and so is one that a `refresh(token)` call overtook: its rotation is stored only while `load` still returns the refresh token it exchanged. An abandoned exchange is one whose connection ended, or whose `exchange` did not settle within the client `timeout`; a result that arrives after the timeout is stored in that way, so the issuer's rotation is not lost. The check and the store are two steps, so a rotation another tab stores between them can be overwritten by that late result; take a lock inside `exchange` (for example the Web Locks API) where that matters. That check reads `load` too: when it throws `UnauthorizedError`, the rotation is not stored and the session ends at once, and any other error from it is reported as `tokenStore`. The SDK bounds only `exchange` by the timeout: a `load` or `store` that never settles blocks the token fetch, as a `getToken` that never settles does, and the application must make its storage settle.

**Refusal run and grace.** A refused refresh token is not a dead session at once. The first refusal starts a refusal run and the clock of its grace horizon. The SDK reads that clock from a monotonic source, so a change of the wall clock cannot move the horizon. Within the run the SDK reads `load` again after each refusal: a different value is presented at once, in the same attempt, even past the horizon; an empty value ends the session at once; the same value is presented again once: while connecting at a random moment inside the remaining grace, while renewing after the refresh retry delay; a second refusal of a value that did not change ends the session, and so does any refusal at the horizon. Each refused attempt inside the horizon is reported as an `error` with the message `refresh token refused, retrying within the grace`, and never with a token. The session ends with `disconnected` code `1`, and the SDK stores nothing more. The run survives a transport loss and a reconnect, so a client that reconnects in a loop still ends at the horizon. A successful exchange closes the run, and so does the server accepting the access token of the connection: a connect reply with a user to a connect that sent a token, or a refresh with a token (`refresh(token)` or a renewal). A later refusal then starts a run of its own with a fresh horizon. The run also ends with the connection for good (a server disconnect that does not reconnect), and with `disconnect()` called by the application.

The horizon is the grace the issuer publishes: `exchange` returns `grace`, in seconds, with each accepted result, and the value is kept for the next run. Without a published grace the option's `grace` applies, and without that the default of 30 seconds. A value above 300 is clamped to 300; a negative or non-finite value is ignored. Setting `grace: 0` makes a refusal of an unchanged token terminal at once. The option is checked when the client is created: `grace` must be a finite number of seconds, 0 or more.

**Refusals by name.** `refusalTypes` lists the names of the server errors that mean the issuer refused the refresh token. The issuer answers a refusal with a gRPC status of its choice and the application error name in the `app-type` trailer, for example `REFRESH_TOKEN_REFUSED`; the SDK reads that name from the error and matches it exactly. A rpc rejected with a listed name rejects with `TokenExchangeRefusedError`, an `UnauthorizedError` that carries the server error in `error`. The SDK never looks at the error code, the application code or an HTTP status: a rejection with another name, or with no list set, is an ordinary error, reported and retried with backoff, and it starts no run. The names are the application's own.

**Two clients of one installation.** Inside the grace the issuer answers a consumed refresh token with the same rotated refresh token and a fresh access token. Two clients that exchange the same token therefore both store the same rotated token, and each uses its own access token for its own connection. The server accepts both connections of the user.

**Lock across processes.** The SDK holds no lock and needs none. An installation whose processes must not present different tokens takes the lock inside `exchange`: take it, read the storage under it, call the rpc with the token it read, write the rotated token to the storage, and release the lock. Then resolve with `token` and `grace` but without `refreshToken`. The SDK calls `store` only for a result that has a `refreshToken`, and `store` runs after `exchange` has returned, outside that lock, so a result with `refreshToken` written under the lock would be stored a second time, unlocked, and could overwrite a newer rotation. A storage that is a file is written to a temporary file that is renamed over it, so a `load` in another process never reads a half-written value. The lock is held at most for the client `timeout`, the time the rpc may take.

**Attribution.** The `meta` claim of the access token is the connection's attribution: whatever the issuer needs to tie the connection to an installation, a device or a session. The connection stores the `meta` of the connect at connect, and it replaces it with the `meta` of the access token at every renewal and rebind whose access token carries the claim; a token without it keeps the attribution the connection has, so after the bootstrap the connection carries the attribution of its access token. A proxy with `include_connection_meta` forwards it. The SDK never parses the access token. The exchange call is anonymous, so its attribution is in the request the issuer defines. An issuer that wants a stable attribution across renewals keeps `meta` the same for the access tokens of one session.

**Reconnects and the access token.** A reconnect of the same client keeps its access token while the token is valid: the connect carries it, the reply has a user, and no exchange runs, so a transport loss costs no mint. A new client instance, a new process or a page load, exchanges once at its first connect. The `token` option may seed a cached access token; the SDK then treats its expiry as unknown, and the server decides: a refused token makes the connect anonymous, and the bootstrap runs. Whether to keep the access token across process restarts is the application's choice; the SDK never persists anything.

**Load and the current attempt.** `load` returns the refresh token, or nothing. It may throw: an `UnauthorizedError` is terminal at connect and at renewal, and ends the session as the removed token does; any other error is reported and retried with backoff. Only the current attempt decides. An attempt that a reconnect, a `refresh(token)` call, a timeout or `disconnect()` has superseded drops its outcome, whether that is an empty value, a refusal or an `UnauthorizedError`: a lost connection never ends the session by itself, and the reconnect keeps the access token it held. A renewal that a `refresh(token)` call superseded (one started while it ran) reports nothing, whatever its outcome, and the session goes on: the call decides. A `refresh()` without a token fetches its own token and does not supersede the renewal, so a failure of the renewal is reported and retried as usual.

An exchange holds the queue of the client for up to twice the client `timeout`: the next exchange, which loads the refresh token again, starts once the exchange settles or that long after it started, whichever comes first. The result of an exchange which settles later than that can lose its rotation to the next exchange, so keep `exchange` well under the client `timeout`. An exchange that runs past the `timeout` closes the connection after a backoff that grows with each failed bootstrap, so a stalled exchange cannot make the client reconnect in a loop.

The events an application sees:

| Event | When |
|---|---|
| `connected` | with an empty `user` when `load` returns nothing at connect: the connection is anonymous |
| `error`, type `connectToken` | `load` or `exchange` failed at connect, other than `UnauthorizedError`; retried on the same connection with backoff. An exchange that runs past the client `timeout` closes the connection instead, after a backoff, and the reconnect bootstraps again. A refusal inside the grace horizon is reported here too, with the message `refresh token refused, retrying within the grace` |
| `error`, type `refreshToken` | the renewal failed, or the refresh token was refused inside the grace horizon; retried with backoff |
| `error`, type `tokenStore`, code `6` (`clientRefreshToken`) | `store` threw or rejected; the exchange went on with its access token |
| `disconnected`, code `1` (`unauthorized`) | the session is dead: a second refusal of an unchanged refresh token, or the grace horizon of the refusal run has passed, or `load` returned nothing after a refusal or at renewal, or `load` threw `UnauthorizedError`, all of them for the current attempt. The client does not reconnect |

The server must accept a connection without a token (`client.allow_anonymous_connect_without_token: true`), must allow a refresh that changes the user (`client.rebind.enabled: true`), and the exchange method must be callable by an anonymous connection: a registry entry with `auth_class: anonymous`, whose calls never carry the connection token, so the issuer authenticates the exchange by the refresh token alone. The access token is the connection token: the same `client.token` verification applies, and its `exp` drives the renewal. The issuer refuses a refresh token with any gRPC status and the application error name in the `app-type` trailer; no status transform is needed. The issuer publishes its grace in seconds in each exchange reply, as described above.
